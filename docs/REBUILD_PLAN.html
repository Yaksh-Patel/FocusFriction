FocusFriction Rebuild

A code review of the old app, and the four-phase rebuild — now complete — that turned it into a notes app worth opening daily, one that also pauses the apps you keep reaching for.

Two products, one app

The brief is multipurpose, and that only works if each half stands alone. A notes app nobody would use without the blocker is a to-do list with extra steps; a blocker that needs notes to justify itself is a nag screen.

Half one
A notes app you'd keep with protection off

Full Keep parity — titles, bodies, checklists, colours, pins, labels, archive, search. It has to survive the test of being useful on a day you never open a monitored app once.

Half two
A pause that costs a few seconds of thought

Friction that scales with how often you've already caved today. Always passable, never free — the point is noticing you didn't mean to open the app.

What joins them: the pause screen shows your own note headings. Not a generic “are you sure”, but the four things you wrote down that you actually meant to do — and one tap opens that note instead of the feed. The notes make the pause worth obeying; the pause gives the notes a moment where they matter.

What this changes structurally: notes become the home surface, not a tab beside the blocker. Protection moves from being the app's identity to being a mode it offers. Today the root component gates you into a setup checklist until protection is on — that inverts, so the app is immediately useful before you've granted a single permission.

The interception was never an overlay

Most of what reads as sloppiness traces to one architectural decision. Opening a monitored app doesn't draw a pause screen over it — it cold-boots the entire React Native app and hopes the timing works out.

Current path
FocusAccessibilityService → InterventionActivity → MainActivity — full RN cold start → JS polls for a session
  1. It's a race, and it loses. InterventionActivity starts MainActivity with FLAG_ACTIVITY_NEW_TASK, landing it in a different task. The activity is then destroyed, and its onDestroy clears the active session. By the time JavaScript boots and polls, there's nothing to find — so the app just opens.
  2. When it wins, it's late. A React Native cold start runs one to three seconds. You watch the feed load the whole time. The friction arrives after the dopamine it was meant to prevent.
  3. The inverse failure is worse. Swipe the intervention away mid-session and active_session_* can persist in storage. The accessibility service returns early whenever a session is active, so protection silently stops working entirely until the service reconnects.

The scaffolding for the right answer is already in the tree and unused: canDrawOverlays and requestOverlayPermission sit in InstalledAppsModule.kt, and older builds showed an “Overlay Permission Required” banner. But SYSTEM_ALERT_WINDOW is declared only in app.json — which does nothing, because android/ is committed and prebuild never runs. The real manifest has never had the permission.

The fix, as planned: draw the pause into a system overlay window instead of launching anything. No React Native boot, no task race.

What actually shipped

The overlay was built twice and abandoned. A TYPE_ACCESSIBILITY_OVERLAY window needs no permissions and cannot be hidden by the app underneath — but it is layered above the status bar, the navigation bar and the keyguard. On device that meant the notification shade would not open, the nav buttons were dead, other apps were unreachable, and unlocking the phone returned to the pause screen. The user was trapped.

The shipped answer is PauseActivity: a plain native Activity. It keeps every property that mattered — native, instant, no bridge — and drops the one that caused the damage. The original design's real mistake was never “an Activity”; it was chaining from one Activity into the React Native app and racing its startup.

A second thing changed for the same reason: the pause screen uses no keyboard at all. An EditText in a non-activity window gave no cursor, could not be dismissed, and covered the card. Math got a keypad; the typing challenge became tap-the-words-in-order.

Four phases, in dependency order

Numbered because the order is load-bearing: each phase is verifiable on-device before the next one lands, so there is never a long stretch where nothing runs.

01

Make the current app honest

Done

Every defect above, with no architectural change. Fix the schedule store mismatch, rewrite export/import on the new File/Paths API, hydrate the session manager, correct the three record signatures, wire real daily-open counts so difficulty scales again, cache app icons in a native LruCache, make the debounce per-package, delete the dead files, and replace the deprecated SafeAreaView that warns on every launch.

No dependencies · fully testable alone

02

The native pause screen

Done

Shipped as an Activity, not an overlay. Two overlay designs were built and abandoned — see the correction above. The friction screen is PauseActivity: plain native Kotlin, no React Native, no bridge, no cold start, and an ordinary window that leaves the shade, nav bar and keyguard alone. Plain Android views rather than Compose, which kept several MB out of the APK. Challenge generation, difficulty and outcome logging all moved to Kotlin, because no JavaScript is alive at interception time. InterventionActivity, InterventionModule and InterventionScreen.js deleted.

Needs 01 · deletes code 01 repaired

03

Notes at the centre

Done

Replace flat tasks with a real note model — title, body, checklist items, colour, pinned, archived, labels, timestamps — on expo-sqlite. Keep-style masonry grid, editor, undo-on-delete, search. Notes take over as the home surface and the setup checklist stops gating it, so the app is useful before any permission is granted. A compact heading projection is mirrored into shared storage on every write so the pause screen can read it synchronously.

Material 3 Expressive

Done

Light, dark and system themes with wallpaper-derived dynamic colour. A real vector icon set replacing every emoji used as chrome — the single biggest thing making the app read as unfinished. Elevation and state layers, spring motion, tinted note cards, and a deliberately distinct visual language for the overlay so it never feels like the app followed you.

Decisions locked

Each was chosen over stated alternatives. Recorded so they don't get relitigated in a later session.

Notes storage
SQLite in JS, headings mirrored to native

Over a fully native Room database. The overlay needs a synchronous read at window-change time; mirroring a small projection matches the pattern the policy store already uses.

Interception
Native PauseActivity

Revised during the build. A system overlay window trapped the user above the status bar, nav bar and keyguard; a normal Activity keeps the speed and drops the trap.

Visual scope
Full Material 3 Expressive, dynamic colour

Over keeping the dark-only palette. Touches every screen, but the emoji-as-icon problem can't be fixed halfway.

Sequencing
Repair first, then re-architect

Over leading with the overlay. Slower to the interesting part, far lower risk of a long stretch where nothing works end to end.

Where the Kotlin actually goes

“Natively a notes app” meant identity, not language

The phrase reads two ways. It could mean notes are the heart of the app — flipping it from a blocker with a to-do list stapled on, into a notes app that happens to block. Or it could mean written in Kotlin, Android's own language, rather than the JavaScript layer the app uses today. Confirmed as the first.

The second would have meant discarding all 3,800 lines of working JavaScript and rebuilding every screen from scratch — months of work for a payoff you'd mostly notice as slightly smoother scrolling.

Worth knowing either way: the overlay is Kotlin regardless. A window that draws on top of another app has to live outside your app and appear in a fraction of a second, which React Native cannot do. The native benefit lands exactly where it matters, without paying for it everywhere else.
